结合你现在做过的功能，面试官很容易沿着这条线追问：

**为什么需要它 → 请求怎么走 → 并发是否安全 → 故障时怎么办 → 你如何证明它有效。**

你最值得准备的是下面这些题，尤其是控制面、etcd、热加载和压测这几组。

**1. 项目整体：先确认你是否真正理解自己的架构**

常见问题：

- 介绍一下你的网关项目，解决了什么问题？
- 数据面、配置面、控制面分别是什么？
- 为什么控制面需要独立部署？
- Nacos 和 etcd 都能存数据，为什么同时使用？
- 你的项目与 Nginx、Envoy、APISIX 有什么差距？
- 为什么自己实现，而不直接使用成熟网关？

你要能把职责说清楚：

```
控制面：管理、保存、分发配置，收集应用结果。
Gateway：本地执行路由、鉴权、限流、负载均衡与代理。
etcd：共享配置存储和分布式协调。
Nacos：业务服务实例发现。
```

“为什么自己写”应按学习项目回答：为了理解实现与取舍，再说明边界。不要把它包装成全面替代成熟网关的产品。

**2. 请求链路：面试官可能让你从入口讲到返回**

常见问题：

- 一个请求从进入 Gateway 到返回，经过哪些步骤？
- 认证、限流、路由匹配的顺序为什么这样安排？
- 总超时和单次重试超时有什么区别？
- 客户端取消请求，上游请求会停止吗？
- 转发时如何处理路径、Host、请求头和响应体？
- 为什么使用 `http.Transport`？连接池如何复用？

典型追问：

> 上游已经返回响应头，但响应体一直不结束，超时还能控制吗？

这里考查的是 Context 是否覆盖响应体读取，以及是否正确关闭 Body、释放资源。不能只回答“设置了两秒 timeout”。

另一道容易被问到的是：

> 网关重试一次，Go 的 HTTP Transport 会不会也自动重试？你怎么定义和统计一次真实上游尝试？

需要区分你实现的应用层重试与底层 Transport 的行为。

**3. 热加载：这是你项目里很适合深入讲的亮点**

常见问题：

- 为什么要把 YAML 编译成 Runtime？
- 为什么用 `atomic.Pointer` 替换配置？
- 原子替换指针后，还需要锁吗？
- 配置更新时，旧请求怎么办？
- 新配置非法，为什么不会影响当前服务？
- 旧 Runtime 什么时候释放？
- 热加载后，健康状态、熔断状态和连接池是否会重置？

最可能的深入追问：

> 请求刚拿到旧 Runtime，你就关闭了它，是否有问题？

你需要分清：

```
原子发布：新请求能读到完整的新对象。
生命周期：旧对象何时可以停止、关闭或回收。
```

原子指针不自动解决旧资源的生命周期，也不自动保证内部可变字段线程安全。

还有一个关键问题：

> 如果一个请求在鉴权时读一次 Runtime，在路由时又读一次，会发生什么？

配置更新可能导致同一个请求混用两个版本。你应该解释入口固定快照的设计，以及实际代码是否做到。

**4. etcd 与并发发布：你刚才问的这些，几乎都能成为面试题**

常见问题：

- 为什么选择 etcd？
- 多个控制面同时修改配置，怎么避免覆盖？
- 为什么事务之外还使用分布式锁？
- CAS 能不能替代锁？
- etcd 有复制延迟，为什么 CAS 还能正确？
- 业务版本号、key 的 version、etcd revision 有什么区别？
- 读配置需要分布式锁吗？

面试官可能直接给这个场景：

```
CP1、CP2 都读取 V12
都准备提交 V13
怎么处理？
```

你要能分别解释两种实现：

```
锁：
抢锁 → 读取最新状态 → 分配版本 → 提交 → 解锁

CAS：
读取状态与 revision → 条件事务提交
                   → 冲突后重新读取或返回冲突
```

再追问：

> CP1 拿到锁之后暂停很久，lease 过期，CP2 拿到锁；CP1 恢复后继续写怎么办？

这道题很有区分度。需要想到**锁所有权校验、条件提交或 fencing**，不能只说“有分布式锁就安全”。

**5. 配置分发与故障恢复：重点考查分布式系统边界**

常见问题：

- 为什么使用 SSE，而不是一直轮询？
- 为什么有 SSE 后还要周期性同步？
- ACK 和 NACK 分别代表什么？
- 控制面保存配置成功，是否意味着所有网关已经生效？
- Gateway 如何拒绝过期版本，避免配置倒退？
- 控制面全部宕机，Gateway 能否继续服务？
- Gateway 此时重启，如何恢复？
- 为什么 etcd 模式下不能让旧本地文件重新覆盖远端配置？

典型故障题：

> CP1 已经提交 V13，但还没返回 HTTP 响应就宕机了，管理员重试，会不会生成 V14？

这里考查“请求结果未知”与重复提交处理。你可以结合相同配置去重说明，但要区分内容去重和通用请求幂等。

另一题：

> GW1 ACK V13，GW2 NACK V13，此次发布算成功还是失败？

这没有统一答案，取决于发布策略。你应说明当前实现如何展示状态，是否实现了“全部 ACK 才成功”或自动回滚，不能把观测能力说成已经实现了发布编排。

**6. 负载均衡、健康检查、熔断和限流**

常见问题：

- 主动健康检查与被动摘除有什么区别？
- 为什么收到 500 不一定说明实例网络不健康？
- 节点摘除之后，怎么恢复流量？
- 所有节点都不可用时怎么办？
- 为什么同时需要客户端限流与服务级降级？
- 限 QPS 能不能限制并发请求数？
- 重试为什么可能加重故障？

“QPS 与并发”这题可以举例：

```
同样每秒 100 个请求：

每个请求耗时 10ms：在途请求较少。
每个请求耗时 10s：在途请求会大量积累。
```

所以 QPS 限流、并发上限和超时控制各有作用。

你还可以主动讲：

> 重试增加的是上游尝试量。因此需要区分客户端请求数和上游尝试数，并考虑重试预算。

**7. Go 并发：Mutex/channel 对照是你的现成材料**

常见问题：

- 为什么最后保留 Mutex？
- channel 发送一定不阻塞吗？
- 非阻塞发送如何实现？队列满了怎么办？
- channel 内部是否也涉及锁与同步？
- 如果允许丢事件，会不会影响熔断正确性？
- 原子计数配后台统计，如何保证窗口数据合理？
- goroutine 如何退出？如何避免向已关闭 channel 发送？

你可以用项目经历回答：

> 实现了 Mutex 与非阻塞 channel 两种跟踪方式。正常流量下，Mutex 版本有原子快速路径，很多成功请求不需要加锁；channel 增加了投递和调度成本，因此没有获得稳定收益，最终保留 Mutex 默认实现。

但要注意，你目前多轮压测存在环境污染、有效轮次不对称的问题，**只能说“已有结果没有证明 channel 更优”，不宜宣称已严格证明 Mutex 全面更快。**

一道更深入的题：

> 请求总数和失败数分别用两个 atomic，自增时恰好遇到统计协程 Swap，会不会分到不同窗口？

这是“单变量原子性不等于多字段快照一致性”。要说明是否接受近似统计，以及误差如何影响阈值判断。

**8. 压测、观测与性能定位**

常见问题：

- 你测的是哪个接口？是否经过鉴权和真实上游？
- 为什么 `metrics-smoke` 能达到约 9,500 req/s，之前代理接口只有几百或一千？
- 怎么保证不同方案公平比较？
- 为什么看 P95/P99，而不只看平均延迟？
- Windows `TIME_WAIT` 是怎么影响测试的？
- CPU 不高，吞吐上不去，你怎么排查？
- 如何用 pprof 定位 Mutex、日志和网络的开销？

这组问题回答时要带上实验条件：

```
请求路径、并发数、持续时间
上游故障方式、连接复用
日志与 tracing 设置
预热、执行顺序、重复轮次
错误分类、CPU/GC/连接数
```

尤其不要把“快速拒绝 503 后，总 req/s 上升”当成业务处理能力提高。要分别统计：

- 客户端完成请求吞吐。
- 成功业务吞吐。
- 网关主动拒绝。
- 上游失败与重试量。

**9. 安全与三级缓存：容易被追问，但要区分已做与计划**

安全方面可能问：

- Access Token 与 Refresh Token 为什么分开？
- Refresh Token 为什么存 Hash？
- 轮换是否原子？并发刷新会怎样？
- 登出后，已签发的 Access Token 还能不能使用？
- Admin API 如何保护？JWT 密钥如何管理？
- 为什么控制面和 etcd 之间需要 TLS 或 mTLS？

三级缓存方面可能问：

- 为什么本地缓存会让一致性 Hash 有价值？
- 为什么按资源 key，而不一定按登录用户 ID 路由？
- 扩容、缩容和故障摘除会迁移多少 key？
- 多个 Gateway 实例列表不一致，会发生什么？
- 数据更新后，如何使多个业务实例的 L1 缓存失效？
- 热点 key 都命中一台实例，怎么办？

**如果三级缓存尚未落地，就明确说它是下一阶段设计。**缓存一致性、热点保护和实际命中率，面试官很容易追到实现细节。

准备时，我建议你先把这五道题讲到能画图、能举故障例子：

1. 一次请求和一次配置发布，分别经过哪些组件？
2. Runtime 热切换后，旧请求和旧资源怎么处理？
3. 多控制面并发发布为什么安全，锁失效又怎么办？
4. 控制面、etcd 或网络故障时，系统还能做什么？
5. 为什么选择 Mutex，你的压测证据能支持多强的结论？

这五道答扎实，比记很多网关功能名更有说服力。
