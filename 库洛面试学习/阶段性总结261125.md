## **一、第 6 题：Java 异常体系**

**原题：** 关于 Java 异常体系的说法，正确的是？

A. Error 继承自 Exception。

B. RuntimeException 继承自 Error。

C. Exception 和 Error 都是 Throwable 的直接子类。

D. IOException 属于非受检异常。

**你的答案：D；正确答案：C。**

### **知识点整理**

Java 中所有可以被抛出的异常和错误都继承自 Throwable。其中 Error 通常表示 JVM 或运行环境中比较严重的问题，Exception 则表示程序执行过程中出现的异常情况。

|类型|常见实例|编译器是否强制处理|
|---|---|---|
|受检异常|IOException、SQLException、InterruptedException|是|
|非受检异常|NullPointerException、ArithmeticException|否|
|Error|OutOfMemoryError、StackOverflowError|否|

受检异常必须通过 `try-catch` 捕获，或者使用 `throws` 声明，让异常继续向上层传播。非受检异常则没有这样的编译期要求。

**记忆重点：RuntimeException 及其子类、Error 及其子类属于非受检类型，其他 Throwable 子类属于受检类型。**

## **二、第 17 题：Spring 事务回滚机制**

**原题：** 关于 Spring 的 `@Transactional`，下列说法正确的是？

A. 默认情况下，抛出 RuntimeException 或 Error 会触发事务回滚。

B. 默认情况下，抛出普通的受检异常也一定会触发事务回滚。

C. 同一个类内部通过 this 调用另一个事务方法，通常不会经过事务代理。

D. 只要添加了 @Transactional，无论是否经过 Spring 代理，都能保证事务生效。

**你的答案：BC；正确答案：AC。**

### **1. Spring 默认回滚规则**

|抛出的异常|默认是否触发回滚|
|---|---|
|RuntimeException|是|
|NullPointerException|是|
|ArithmeticException|是|
|Error|是|
|IOException|否|
|SQLException|否|

这里指异常传播到事务代理边界，且没有额外配置回滚规则的情况。

如果希望普通受检异常也触发回滚，可以使用：

```
@Transactional(rollbackFor = Exception.class)
public void createOrder() throws IOException {
    orderMapper.insert(order);
    throw new IOException();
}
```

### **2. Spring 事务为什么会自调用失效？**

Spring 默认通过 AOP 动态代理实现声明式事务。正常情况下，调用方先访问代理对象，代理对象开启事务，再调用目标对象的方法，最后根据执行结果提交或回滚事务。

例如：

```
@Service
public class OrderService {

    public void createOrder() {
        this.saveOrder();
    }

    @Transactional
    public void saveOrder() {
        // 数据库操作
    }
}
```

这里 `createOrder()` 直接调用目标对象自身的 `saveOrder()`，没有经过代理，因此 `saveOrder()` 上的事务注解不会单独生效。如果外层方法已经开启事务，内部方法仍然可以在已有事务中执行，这一点需要区分。

**相关延伸考点：** 异常被 catch 后没有继续抛出、事务传播机制、JDK 动态代理与 CGLIB、跨线程调用事务方法。

## **三、第 21 题：SQL 查询与 LEFT JOIN**

**原题：** 关于 SQL 查询，下列说法正确的是？

A. WHERE 先于 GROUP BY 执行。

B. HAVING 可以对分组后的数据进行过滤。

C. COUNT(*) 统计行数，COUNT(amount) 不统计 NULL。

D. 聚合条件 SUM(amount) > 1000 应当写在 WHERE 中。

E. LEFT JOIN 之后，如果 WHERE 要求右表字段 IS NOT NULL，那么不匹配的左表记录会被过滤掉。

**你的答案：ABC；正确答案：ABCE。**

### **1. SQL 的逻辑执行顺序**

```
FROM
  ↓
JOIN / ON
  ↓
WHERE
  ↓
GROUP BY
  ↓
HAVING
  ↓
SELECT
  ↓
DISTINCT
  ↓
ORDER BY
  ↓
LIMIT
```

这是常见 SQL 查询的逻辑执行顺序，不代表数据库优化器实际执行操作的物理顺序。

### **2. LEFT JOIN 与 WHERE 的区别**

假设有两张表：

**orders 表**

|id|user_id|
|---|---|
|1|101|
|2|102|
|3|103|

**users 表**

|id|name|
|---|---|
|101|Alice|
|102|Bob|

执行 LEFT JOIN：

```
SELECT o.id, u.name
FROM orders o
LEFT JOIN users u ON o.user_id = u.id;
```

结果：

|id|name|
|---|---|
|1|Alice|
|2|Bob|
|3|NULL|

如果增加 WHERE 条件：

```
SELECT o.id, u.name
FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE u.id IS NOT NULL;
```

结果：

|id|name|
|---|---|
|1|Alice|
|2|Bob|

因为 LEFT JOIN 先生成连接结果，无法匹配的右表记录用 NULL 填充，随后 WHERE 再过滤这些记录。

**核心区别：ON 决定哪些记录能够匹配，WHERE 决定哪些连接结果能够被保留。**

## **四、第 22 题：双指针与 ACM 输入输出**

**原题：** 将数组中的奇数移动到前面，偶数移动到后面，要求时间复杂度 O(n)，空间复杂度 O(1)。

你的算法完全正确，扣分原因是没有处理标准输入输出，而是使用了固定数组进行测试。

### **ACM 模式完整代码**

```
import java.util.Scanner;

public class Main {

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        int n = scanner.nextInt();
        int[] nums = new int[n];

        for (int i = 0; i < n; i++) {
            nums[i] = scanner.nextInt();
        }

        int left = 0;

        for (int right = 0; right < n; right++) {
            if (nums[right] % 2 != 0) {
                int temp = nums[left];
                nums[left] = nums[right];
                nums[right] = temp;

                left++;
            }
        }

        StringBuilder sb = new StringBuilder();

        for (int i = 0; i < n; i++) {
            if (i > 0) {
                sb.append(" ");
            }
            sb.append(nums[i]);
        }

        System.out.println(sb);
    }
}
```

正式笔试需要注意，ACM 模式通常要求自行读取输入、处理数据、输出结果，而不是像力扣一样只实现指定方法。另外，对于大量输入数据，Scanner 可能成为性能瓶颈，后续需要掌握 BufferedReader 或自定义快速输入。

这道题不需要重新学习算法，主要补充 ACM 模式的代码编写能力。

## **五、第 23 题：多重背包动态规划**

**原题：** 给定 N 种物品，每种物品有重量、价值和数量限制，求容量为 W 的背包可以获得的最大价值。

### **1. 原代码错误**

你的核心状态转移代码：

```
for (int i = 0; i < n; i++) {
    for (int j = 0; j < count[i]; j++) {
        for (int k = space + 1; k >= weights[i]; k--) {
            dp[i] = Math.max(
                dp[i],
                dp[i - weights[i]] + values[i]
            );
        }
    }
}

return dp[space + 1];
```

存在以下问题：

|错误代码|正确代码|
|---|---|
|`k = space + 1`|`k = space`|
|`dp[i]`|`dp[k]`|
|`dp[i - weights[i]]`|`dp[k - weights[i]]`|
|`dp[space + 1]`|`dp[space]`|

根本原因是没有始终围绕 DP 数组的状态定义编写代码。

`dp[k]` 表示背包容量为 k 时，在已经处理的物品中能够获得的最大价值。因此 dp 的下标是背包容量，而不是物品下标。

### **2. 三种背包问题的区别**

|类型|每种物品可选数量|容量遍历方向|
|---|---|---|
|0-1 背包|0 或 1 个|倒序|
|完全背包|无限个|正序|
|多重背包|有限个|拆分成 0-1 背包后倒序|

三者的一维 DP 核心状态转移方程相同：

\[ dp[j]=\max(dp[j],dp[j-w_i]+v_i) \]

区别在于如何控制物品的使用次数。

### **3. 为什么需要二进制拆分？**

假设某种物品有 13 个，直接拆分需要执行 13 次 0-1 背包，而采用二进制拆分只需要处理 4 组：

\[ 13=1+2+4+6 \]

**二进制拆分演示**

选择不同的物品组，观察能够组合出的物品数量。

1个物品

2个物品

4个物品

6个物品

当前选择数量

# **0** **/ 13**

尚未选择物品

重置

每组物品作为一个独立的 0-1 背包物品，就能够组合出 0～13 之间的任意物品数量。

### **4. 正确的优化代码**

```
public int dpSolution(int[] weights, int[] values,
                      int[] count, int space, int n) {

    int[] dp = new int[space + 1];

    for (int i = 0; i < n; i++) {

        // 限制实际能够装入背包的数量
        int num = Math.min(count[i], space / weights[i]);

        // 二进制拆分
        for (int j = 1; num > 0; j *= 2) {

            int size = Math.min(j, num);

            int weight = weights[i] * size;
            int value = values[i] * size;

            // 0-1 背包
            for (int k = space; k >= weight; k--) {
                dp[k] = Math.max(
                    dp[k],
                    dp[k - weight] + value
                );
            }

            num -= size;
        }
    }

    return dp[space];
}
```

时间复杂度为 \(O(NW\log W)\)，空间复杂度为 \(O(W)\)。

**需要养成的习惯：写任何动态规划题之前，先明确状态定义、状态转移方程、初始化条件、遍历顺序、返回值这五个问题，再开始编写代码。**

## **六、第 24 题：Linux Java 进程 CPU 飙高排查**

**原题：** Linux 服务器上的 Java 服务 CPU 使用率突然达到 500%，如何定位到具体的 Java 线程和代码？

你的错误主要是没有记住具体命令，以及将 CPU 性能分析与 JVM 内存分析混淆了。

### **1. 定位 CPU 使用率高的进程**

```
top
```

查看系统中的进程及其 CPU、内存使用情况，假设找到 Java 进程 PID 为 4567。

### **2. 定位 CPU 使用率高的线程**

```
top -H -p 4567
```

`-H` 表示以线程为单位展示信息，`-p` 表示指定进程。注意是大写 H，小写 `-h` 通常用于查看帮助信息。

假设发现线程 TID 为 4582。

### **3. 将线程 ID 转换为十六进制**

```
printf '%x\n' 4582
```

输出：

```
11e6
```

JVM 线程堆栈中的本地线程 ID（nid）通常使用十六进制表示，因此需要进行转换。

### **4. 导出线程堆栈**

```
jstack 4567 > thread.txt
```

`jstack` 用于获取指定 JVM 进程的线程堆栈，`>` 将结果写入文件。

### **5. 查找对应线程**

```
grep -A 30 'nid=0x11e6 ' thread.txt
```

`-A 30` 表示显示匹配行及其后面的 30 行内容，通过该命令可以找到线程对应的 Java 调用栈。

### **6. 分析具体原因**

找到堆栈之后，需要关注线程状态、线程执行的方法以及具体代码行。CPU 飙高可能是由业务代码死循环、大量计算、CAS 自旋竞争、频繁 GC 等原因导致的。通常需要多次采集线程堆栈，判断该线程是否持续执行相同的方法。

如果怀疑频繁 GC：

```
jstat -gcutil 4567 1000
```

该命令每隔 1000 毫秒输出一次 GC 相关统计信息，可以观察垃圾回收次数及耗时的变化。

### **常见 JVM 排查工具对比**

|工具|主要用途|
|---|---|
|top|查看进程、线程 CPU 和内存使用率|
|jps|查看 Java 进程|
|jstack|查看线程堆栈、排查死锁和线程执行情况|
|jstat|查看 GC 和 JVM 运行统计|
|jmap|查看堆内存相关信息、导出堆转储|
|jcmd|执行 JVM 诊断命令|
|MAT|分析堆转储、排查内存泄漏|
|Arthas|在线诊断 Java 应用|
|async-profiler|CPU、内存分配等性能采样|

**记忆完整排查链路：**

```
top
  ↓
top -H -p PID
  ↓
找到高 CPU 线程 TID
  ↓
printf '%x\n' TID
  ↓
jstack PID
  ↓
grep 查找 nid
  ↓
分析线程状态及具体代码
```
