==🟡1.epoll 有两种触发模式：==

- **LT（水平触发）**：只要缓冲区还有数据未读取，就可以持续通知你。
    
- **ET（边缘触发）**：只有数据状态发生变化时才通知，例如从无数据变为有数据。
    

假设 Socket 缓冲区有 10KB 数据，你每次只读取 1KB：

- LT：剩余 9KB 时，仍然可以再次通知。
    
- ET：可能不会再次通知，因为缓冲区一直处于可读状态，没有发生新的边缘变化。
    

所以 ET 通常需要配合非阻塞 I/O，循环读取直到返回 `EAGAIN`。

**额外记忆：** ET 不等于异步 I/O。epoll 本身属于 I/O 多路复用机制。


==🔴2.Java 只有值传递（Pass by Value），对象参数传递的是**引用的副本**，不是对象本身。==

这里要区分两种操作：

**1. 修改对象内部属性**

```
static void change(Person p) {
    p.name = "Bob";
}
```

方法内外的引用都指向同一个对象，因此调用后原对象的属性也会改变。

**2. 重新给参数赋值**

```
static void change(Person p) {
    p = new Person("Charlie");
}
```

这里只修改了局部引用副本的指向，不会改变调用方的引用。

这也是 Java 面试中非常经典的考点。与你上传的 Java 面试资料中的「值传递和引用传递的区别」一致。

==🔴4.这道题考察的是 Java 的**静态方法隐藏（Method Hiding）和实例方法重写（Method Overriding）**。==

class Parent {
    static void m() {
        System.out.print("P");
    }

    void n() {
        System.out.print("p");
    }
}

class Child extends Parent {
    static void m() {
        System.out.print("C");
    }

    @Override
    void n() {
        System.out.print("c");
    }
}

public class Main {
    public static void main(String[] args) {
        Parent obj = new Child();
        obj.m();
        obj.n();
    }
}

A. `Pc`

B. `PC`

C. `Cc`

D. `Cp`

**请选择一个答案，并解释为什么两个方法的调用结果可能不同**

关键区别在于：

**1. 静态方法：编译时确定**

```
Parent obj = new Child();
obj.m();
```

`m()` 是静态方法，调用哪个方法取决于引用变量的声明类型 `Parent`，所以调用 `Parent.m()`，输出 `P`。

子类定义同名静态方法属于方法隐藏，不是多态意义上的重写。

**2. 实例方法：运行时确定**

```
obj.n();
```

`n()` 是实例方法，遵循动态绑定。虽然引用类型是 `Parent`，但实际对象是 `Child`，所以调用 `Child.n()`，输出 `c`。

记住一句话：**静态方法看引用类型，实例方法看实际对象类型。**


### ==🔴5.**图的 BFS（单选）**==

对于一个无权无向图，要求求出起点到所有其他节点的最短路径长度，以下说法正确的是？

A. 使用 DFS 即可保证第一次访问节点时得到最短路径。

B. 使用 BFS，并在节点入队时标记 visited，可以在 \(O(V+E)\) 时间内完成遍历。

C. 必须使用 Dijkstra 算法，BFS 无法求最短路径。

D. BFS 的时间复杂度一定是 \(O(V^2)\)。

**请选择一个答案，并说明为什么 BFS 能求无权图的最短路径。**

BFS（广度优先搜索）能够求无权图最短路径，是因为它按照距离起点的层数逐层扩展。

例如：

```
       A
      / \
     B   C
    /     \
   D       E
    \     /
       F
```

从 A 开始：

- 第 0 层：A
    
- 第 1 层：B、C
    
- 第 2 层：D、E
    
- 第 3 层：F
    

BFS 保证先访问距离近的节点，再访问距离远的节点，因此第一次访问某个节点时，就已经得到它的最短路径长度。

**一个重要细节：** 应该在节点入队时标记 `visited`，而不是出队时。这样可以避免同一个节点被多个相邻节点重复加入队列。

使用邻接表时，时间复杂度为：

\[ O(V+E) \]

### ==🔴**8.Redis ZSet 与分布式锁（多选题，4 分）**==

关于 Redis，下列说法正确的是？

A. ZSet 中的 member 具有唯一性。

B. ZSet 按 score 排序，score 相同时还会按照 member 的字典序排序。

C. Redis 中所有 ZSet 都一定使用跳表和哈希表实现。

D. Redis 分布式锁释放时，应当通过原子操作比较锁的持有者标识，再删除锁。

这里特别提醒：**Redis 分布式锁最容易考的是为什么不能直接 DEL 解锁。** 因为锁可能已经过期并被其他客户端重新获取，旧客户端直接删除就会误删别人的锁。


### ==🟡**9.MySQL SQL 查询（多选题，4 分）**==

现在有一张订单表：

```
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    amount DECIMAL(10, 2),
    status INT,
    created_at DATETIME
);
```

关于 SQL 查询，下列说法正确的是？

A. SQL 逻辑执行过程中，WHERE 先于 GROUP BY 执行。

B. HAVING 可以对分组后的数据进行过滤。

C. COUNT(*) 统计行数，而 COUNT(amount) 不统计 amount 为 NULL 的行。

D. 聚合条件 `SUM(amount) > 1000` 应当直接写在 WHERE 中。

E. LEFT JOIN 之后，如果 WHERE 条件要求右表某个字段 IS NOT NULL，那么不匹配的左表记录会被过滤掉。

正确答案是 **ABCE**，你漏选了 E。

逐项分析：

- **A 正确**：逻辑执行顺序中，WHERE 在 GROUP BY 之前。
    
- **B 正确**：HAVING 用于过滤分组后的结果。
    
- **C 正确**：`COUNT(*)` 统计行数，`COUNT(amount)` 忽略 NULL。
    
- **D 错误**：`SUM()` 是聚合函数，聚合条件应该放在 HAVING 中，而不是 WHERE 中。

例如：

```
SELECT *
FROM orders o
LEFT JOIN user u ON o.user_id = u.id
WHERE u.id IS NOT NULL;
```

这实际上会过滤掉没有匹配用户的订单，效果类似 INNER JOIN。




## ==🔴**10.Linux CPU 飙高排查（场景题，8 分）**==

线上 Linux 服务器运行了一个 Java 服务，突然 CPU 使用率达到 500%。


请回答：

1. 如何通过 Linux 命令查看该 Java 进程内部各个线程的 CPU 使用情况？
    
2. 假设找到一个 CPU 占用很高的线程，其 TID 为 4582，如何通过命令将其转换为十六进制？
    
3. 如何通过 `jstack` 找到对应的 Java 线程堆栈？
    
4. 找到堆栈之后，你会重点关注哪些信息？
    

**要求给出具体命令，而不是只回答使用什么工具。**
## **一、正确的排查流程**

### **1. 查看进程内各个线程的 CPU 使用率**

```
top -Hp 4567
```

参数含义：

- `-H`：以线程为单位展示信息，注意是大写 H。
    
- `-p`：指定需要监控的进程 PID。
    
- `4567`：Java 进程的 PID。
    

假设得到以下结果：

|线程 TID|CPU 使用率|
|---|---|
|4582|99.8%|
|4583|85.2%|
|4584|0.3%|

这样就可以定位到 CPU 使用率较高的线程。

### **2. 将线程 ID 转换为十六进制**

```
printf '%x\n' 4582
```

输出：

```
11e6
```

其中 `%x` 表示将整数转换为十六进制，`\n` 表示换行。

之所以需要转换，是因为 Linux 的 `top` 显示的是十进制线程 ID，而 JVM 线程堆栈中的 `nid` 通常使用十六进制表示。

### **3. 获取 JVM 线程堆栈**

```
jstack 4567 > thread.txt
```

`jstack` 用于获取指定 JVM 进程的线程堆栈，`>` 将输出重定向到 `thread.txt` 文件。

然后查找对应的线程：

```
grep -A 30 'nid=0x11e6 ' thread.txt
```

`-A 30` 表示除了匹配行，还显示其后面的 30 行内容。

假设得到：

```
"http-nio-8080-exec-7" #35
   nid=0x11e6 runnable

   java.lang.Thread.State: RUNNABLE
       at com.example.OrderService.calculate(OrderService.java:85)
       at com.example.OrderController.create(OrderController.java:42)
```

这样就可以定位到具体的 Java 方法，甚至是具体代码行。

### **4. 分析线程堆栈**

你回答的对象存活时间属于 JVM 内存分析的范畴，而 CPU 飙高主要需要关注线程正在执行什么代码。

|排查对象|可能存在的问题|
|---|---|
|业务线程|死循环、复杂计算|
|GC 线程|频繁垃圾回收|
|CAS 操作|高频自旋、竞争激烈|
|正则表达式|大量回溯计算|
|线程状态|RUNNABLE、BLOCKED、WAITING|
|方法调用栈|定位具体类、方法、代码行|

实际排查时，最好间隔几秒多次执行 `jstack`，观察高 CPU 线程是否持续停留在相同的代码位置。单次堆栈快照不一定能准确反映问题。

如果怀疑是频繁 GC 导致的 CPU 飙高，还可以使用：

```
jstat -gcutil 4567 1000
```

每隔 1000 毫秒输出一次 JVM 垃圾回收相关统计信息。
